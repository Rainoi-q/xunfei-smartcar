## 分层架构（答辩用一张图）

```
                 ┌──────────────────────────── mission_manager ────────────────────────────┐
                 │  二维码/手动指令 → IDLE → NAVIGATING → DOCKING → DONE / FAILED           │
                 └───────┬───────────────────────┬──────────────────────────┬──────────────┘
                         │ /mission/nav_start    │ /control/parking_enable  │ /control/*_enable
                         ▼                       ▼                          ▼
  厂家相机 ──► vision_detect ──► line_follower ─┐                     parking
  厂家雷达 ──► obstacle_avoider ─┐              ├──► cmd_vel_arbiter ──► /cmd_vel ──► 厂家底盘
  厂家深度 ─┘                    └──(scale/bias)┘        ▲
                                                         │ 导航阶段让权
  厂家 nav2 ──(NavigateToPose)── waypoint_nav ───────────┘ (nav2 直接发 /cmd_vel)

  lighting_adaptor ──► 亮度档位 + 曝光        ocr_reader ──► 文本
  hud ◄── 以上所有话题的状态 JSON ──► /hud/image ──► web_video_server
```

**设计要点**（答辩时能说清这三点就够）：

1. **单一速度出口**：只有 `cmd_vel_arbiter` 往 `/cmd_vel` 发。优先级
   急停 > 导航 > 泊车 > 巡线，所有来源 0.5 s 断流自动归零。
2. **感知/控制解耦**：视觉节点只发"偏移量/二维码"，控制节点只吃结构化输入，
   所以同一份 `core.py` 能同时跑在相机、视频回放和虚拟仿真上。
3. **核心逻辑无 ROS 依赖**：`*/core.py` 都是纯函数/纯类，`tests/` 直接 pytest，
   上车前就能把逻辑跑通（102 个用例，0.3 s 跑完）。

## 与"方案一"的差异（PPT 里建议主动说明）

- 原计划 14 项里 ① ② ③ ⑧ ⑩ 本轮**主动不做**（硬件/时间原因），
  改把 ④⑤⑥⑦⑨⑪⑫⑬⑭ 做深：每项都有算法核心 + 单元测试 + 可视化证据。
- 原计划用 Gazebo 做仿真，实际用轻量 2D 仿真（`virtual_sim`）：
  无需显卡/大内存，RDK X5 上也能实时跑，且相机/雷达/深度话题与实车完全同名。
- 语义解析/多指令不做后，`mission_manager` 简化为"一个二维码 = 一个目的地"，
  但保留了 `/mission/event` 里的完整订单 JSON，方便以后接 ②③。
